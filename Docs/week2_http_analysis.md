# Week 2 — HTTP Request/Response Analysis

**Project:** Automated Web Application Security Assessment for Financial Platforms
**Target application:** OWASP Juice Shop (local Docker lab)
**Target URL:** `http://127.0.0.1:3000`
**Author:** Robert Mayonde · Programme: Cybersecurity · JPR Solutions
**Reporting period:** Week 2 of 12 — Python for Security & HTTP Fundamentals
**Scope:** Authorised local lab only. No real credentials, no exploitation.

---

## 1. Objective

Document how a browser and a Python client communicate with a web application over
HTTP, using OWASP Juice Shop as a controlled target. The analysis covers:

- The HTTP GET request issued by the Python script (`Src/http_basics.py`).
- The HTTP request/response exchange observed during a login attempt.
- HTTP methods, status codes, headers, cookies, and transport security.

---

## 2. Method

1. OWASP Juice Shop was run locally in Docker and reached at `http://127.0.0.1:3000`.
2. `Src/http_basics.py` sent a GET request using the Python `requests` library and
   saved the structured result to `reports/week2_http_report.json`.
3. Google Chrome Developer Tools (Network tab) was used to inspect the login
   request and response generated by the application.

All testing was restricted to the deliberately vulnerable application in the local
lab environment.

---

## 3. Script-Generated GET Request

Source of evidence: `reports/week2_http_report.json`.

| Item | Observed result |
|------|-----------------|
| Requested URL | `http://127.0.0.1:3000` |
| Final URL | `http://127.0.0.1:3000/` |
| Method | GET |
| Status code | `200 OK` |
| Content-Type | `text/html; charset=UTF-8` |
| Server header | Not present (`null`) |
| Response size | 9393 bytes |
| Cookies received | None |

### 3.1 Security-relevant response headers

| Header | Observed value | Note |
|--------|----------------|------|
| `X-Content-Type-Options` | `nosniff` | Present — mitigates MIME sniffing |
| `X-Frame-Options` | `SAMEORIGIN` | Present — limits clickjacking via framing |
| `Content-Security-Policy` | Not present | Missing — no CSP defined |
| `Strict-Transport-Security` | Not present | Not applicable over plain HTTP; expected on HTTPS |
| `Referrer-Policy` | Not present | Missing |
| `Permissions-Policy` | Not present | Missing (`Feature-Policy: payment 'self'` present instead — legacy header) |

**Interpretation:** The `200 OK` confirms the script can reach and read the
application. Some protective headers are present, but `Content-Security-Policy`,
`Referrer-Policy`, and a modern `Permissions-Policy` are absent. The absence of a
`Server` header slightly reduces version disclosure. These are *observations for
further review*, not confirmed vulnerabilities. A successful page retrieval does
not imply the application is secure.

## 4. Login Request/Response Analysis

Source of evidence: Chrome Developer Tools (Network tab) during a login attempt.
Screenshots are retained separately with credentials and tokens redacted.

### 4.1 Request

| Field | Observed result |
|-------|-----------------|
| Request URL | `http://127.0.0.1:3000/rest/admin/application-configuration` |
| HTTP method | GET |
| Request Content-Type | `application/json` |
| Example injected input | `' or 1=1 --` style payload (`"1" = '1`) |
| Origin header | Not present |
| Authentication result | Unsuccessful |

> The login form submits credentials to the authentication API. The capture above
> also shows a supporting configuration request made by the single-page frontend.
> In Juice Shop, the actual credential submission is a **POST** to `/rest/user/login`
> with a JSON body `{ "email": "...", "password": "..." }`; this should be captured
> and documented alongside the configuration request for completeness.

### 4.2 Response

| Field | Observed result |
|-------|-----------------|
| HTTP status code | `500 Internal Server Error` |
| Response Content-Type | `application/json; charset=utf-8` |
| `Set-Cookie` header | Present |
| Authentication outcome | Error (not authenticated) |

### 4.3 Interpretation

- The exchange shows how the browser submits authentication data and how the server
  replies. The request method and JSON payload explain how input reaches the server;
  the status code and body explain how the server handled it.
- A `500` response to a malformed/injected input suggests the input was not handled
  gracefully. Server errors can leak implementation detail in their body and warrant
  review for **excessive information disclosure**.
- A `Set-Cookie` header indicates session state is issued; its `HttpOnly`, `Secure`,
  and `SameSite` attributes should be verified (the lab runs over plain HTTP, so
  `Secure` cannot be effective here).

## 5. HTTP Fundamentals Referenced

- **Methods:** `GET` retrieves resources; `POST` submits data such as credentials.
- **Status codes:** `200` success · `302` redirect · `401` auth required ·
  `403` forbidden · `404` not found · `500` server error.
- **Headers:** request/response metadata (e.g. `Content-Type`, `Set-Cookie`,
  `Content-Security-Policy`) that also carry security meaning.
- **Cookies & sessions:** session cookies track authenticated state; `HttpOnly`,
  `Secure`, and `SameSite` reduce cookie-related risk.
- **HTTP vs HTTPS:** HTTP is unencrypted; HTTPS (TLS) protects credentials and
  session data in transit. Financial platforms must use correctly configured HTTPS
  in production.

---

## 6. Security Observations (assessment areas, not confirmed findings)

1. **Transport security** — credentials/session data must travel over HTTPS in
   production; the lab's plain HTTP is for controlled testing only.
2. **Missing security headers** — `Content-Security-Policy`, `Referrer-Policy`, and
   a modern `Permissions-Policy` were not observed on the home page.
3. **Error handling** — the `500` on malformed login input should be reviewed for
   information disclosure and robustness.
4. **Session cookies** — verify `HttpOnly`, `Secure`, and `SameSite` attributes on
   issued cookies.
5. **Input handling** — authentication input should be validated and parameterised.

Each item requires evidence from the test environment before being treated as a
vulnerability.

---

## 7. Limitations

- `Src/http_basics.py` performs a single GET request, not a vulnerability scan.
- The login analysis reflects only the requests/responses observed in the selected
  test cases.
- A successful HTTP response does not establish that the application is secure.
